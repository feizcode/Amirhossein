# راهنمای انتشار و تحویل

این راهنما آرتیفکت عملیاتی است؛ اجرای انتشار، بازیابی یا تغییر زیرساخت در این درخواست انجام نشده است. جزئیات مسیرهای هاست در [راهنمای اصلی استقرار](../../docs/DEPLOYMENT.fa.md) و [بازیابی](../../docs/RESTORE.fa.md) آمده‌اند.

## وضعیت مبنا

نسخهٔ `1.0.0` طبق manifest و STATUS روی `https://amir.feizai.ir` منتشر شده است. PHP 8.2.30، MariaDB 10.1.48، HTTPS و restore در شواهد قبلی تأیید شده‌اند. این وضعیت در زمان این تدوین دوباره از شبکه بررسی نشده است.

ریشهٔ عمومی `/home/feizaiir/public_html/amir/` فقط ورودی و assets دارد؛ کد، vendor، config و storage در `/home/feizaiir/amir-app/` خصوصی‌اند. تنظیم PHP فقط همین زیردامنه است. نصب SQL اولیه فقط برای DB خالی است؛ ابزار ارتقای DB جاری نیست.

## پیش از انتشار بعدی

- [ ] نسخه و دامنهٔ تغییر، نیازمندی و تصمیم مرتبط معلوم باشد.
- [ ] نسخهٔ خصوصی داده و `config/local.php` جدا حفظ و قابل بازیابی باشد.
- [ ] برای تغییر schema، migration نسخه‌دار و سازگاری rollback مشخص باشد.
- [ ] تست متناسب با تغییر، lint، validation و build همان نسخه پاس شده باشند.
- [ ] بستهٔ ZIP حاوی vendor و assets آماده و فاقد config واقعی، رمز، توکن، SQLite، دادهٔ نمونه و ابزار نصب موقت باشد.
- [ ] SHA-256 و اندازهٔ بسته در manifest ثبت و فایل واقعی با آن تطبیق شود.
- [ ] پنجرهٔ تغییر و مسئول برگشت برای تغییر اثرگذار بر داده مشخص باشد.

فرمان‌های ساخت موجود در پروژه:

```text
php tests/run.php
node tests/browser.cjs
php bin/export-sql.php
pnpm build
node bin/package.cjs
```

آزمون مرورگر دادهٔ توسعه را بازنشانی می‌کند. `export-sql` و `package` فایل خروجی می‌نویسند؛ manifest بستهٔ تازه ابتدا `deployed:false` دارد. فقط بعد از استقرار و شاهد محیط واقعی باید وضعیت انتشار را ثبت کرد. ابزار فعلی، Artifacts را خودکار در بستهٔ سورس قرار نمی‌دهد؛ TASK-04 باز است.

## هنگام استقرار

۱. بستهٔ آماده را در مسیر درست باز کنید؛ فایل خصوصی به public_html منتقل نشود. `config/local.php` و storage موجود حفظ شوند. مجوز فایل عمومی ۶۴۴، پوشه ۷۵۵، فایل خصوصی ۶۰۰ و storage خصوصی ۷۰۰ مطابق راهنمای پروژه‌اند.

۲. برای ارتقا فقط migration همان نسخه و در DB همین پروژه اجرا شود؛ SQL اولیه روی دادهٔ موجود وارد نشود. قبل از تغییر ناسازگار، برنامه از دسترس نوشتن خارج شود.

۳. PHP و افزونه‌ها در دامنهٔ مستقل تأیید شوند؛ تنظیم عمومی حساب و دامنهٔ اصلی تغییر نکند. ابزار موقت نصب/تست پس از کار حذف و دسترسی موقت باطل شود.

## بررسی پس از انتشار

- [ ] HTTP به HTTPS معتبر هدایت می‌شود؛ زنجیره و دامنهٔ گواهی درست‌اند.
- [ ] بدون نشست صفحهٔ خصوصی به login و API به 401 می‌رسد؛ ورود و خروج کار می‌کنند.
- [ ] مسیرهای config، storage، vendor و فایل backup مستقیم دادهٔ خصوصی نمی‌دهند.
- [ ] ثبت/ویرایش، تکلیف، منبع و گزارش با دادهٔ آزمون کنترل‌شده درست‌اند؛ نوشتن آزمایشی ترجیحاً روی محیط جدا انجام شود.
- [ ] نشست دوم دادهٔ ذخیره‌شده را می‌بیند؛ درصد تکراری نمی‌شود و بازهٔ گزارش درست است.
- [ ] دانلود بکاپ احرازشده و restore همان فایل در DB جدا تطبیق داده می‌شود.
- [ ] فقط رکوردهای آزمون دارای شناسهٔ معلوم پاک شوند؛ بازنشانی کل دفتر تولید روش پاک‌سازی نیست.
- [ ] نسخه، هش، محیط، نتایج و مسئله‌های باز در evidence/STATUS ثبت شوند.

## برگشت و حادثه

اگر smoke شکست خورد، نوشتن را متوقف و نوع خرابی را مشخص کنید. برای تغییر کدِ سازگار با DB، کد و assets نسخهٔ سالم قبلی با حفظ config/storage بازگردند. برای migration ناسازگار، rollback داده فقط با نسخهٔ حفظ‌شده و برنامهٔ مشخص انجام شود؛ restore همهٔ داده‌های بعد از snapshot را جایگزین می‌کند.

قبل از restore از وضعیت فعلی و config نسخهٔ خصوصی بگیرید. فایل gzip و SQL بازیابی بیرون ریشهٔ وب بمانند. دستور `bin/restore.php` داده را در تراکنش جایگزین می‌کند؛ مسیر دوم `bin/backup-to-sql.php` و واردکردن در DB همان پروژه است. پس از restore تعداد رکورد، تاریخ قدیمی، منابع بایگانی و پیشرفت را تطبیق و با نشست تازه بررسی کنید. راهنمای قدیمی PHP 8.4 می‌گوید؛ پیش از اجرا با قرارداد ^8.2 و محیط واقعی تطبیق شود (TASK-02).

## نگه‌داری باز

TLS طبق شاهد موجود در `2027-01-18T11:13:47Z`، یعنی ۱۸ ژانویهٔ ۲۰۲۷ ساعت ۱۴:۴۳:۴۷ تهران، منقضی می‌شود. تمدید خودکار تأیید نشده است؛ TASK-01 باید مسئول و روش قابل اتکا تعیین کند. این سند یادآور یا اتوماسیون زمان‌بندی‌شده ایجاد نکرده است.

بکاپ در اولین استفادهٔ روز ساخته و هفت نسخهٔ روزهای استفاده نگه داشته می‌شود؛ فایل روزانه با نوشتن‌های بعدی تازه نمی‌شود. نسخهٔ خارج از هاست و RTO مشخص نیستند. TASK-03 برای توافق و اندازه‌گیری باز است. گزارش پذیرش قبلی را با پایش عملیاتی دائمی یکی نگیرید.
